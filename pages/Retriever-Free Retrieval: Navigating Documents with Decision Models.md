- 何をする手法か
    - 埋め込みの近さで探す代わりに、[[Jev]]のような判定モデル(トークンを生成せずに選択肢の確率を返す)で文書を選ぶ
    - 候補を一つの文脈に並べ、候補ごとに「関係あるか」をYes/Noで訊き、P(Yes)で順位をつける
    - 文書集合を木(大きな話題→文書→段落)にして、上から各段で残す枝を判定する
- 割り引いて読むところ
    - 見出しの「8Bのrerankerより+13.8」は、ほとんどが判定器(Jev)の強さから来ている
    - 同じJevで埋め込み検索の上位100件を並べ替えると、MultiDoc2Dialで49.9対51.2、MTRAGで38.3対38.7(Table 8)
    - 木を辿ることの効果が出たのはConditionalQAとNatural Questionsだけ(約+7)
    - 「retriever-free」と言いつつ、Wikipediaの木はe5の埋め込みとk-meansで事前に作っている

- [[LLM Wiki]]のindex.mdが肥大化したときの対策として使えるかを、一晩試した(2026-11-05)
    - Claude Code(Opus 5.5)が論文を読み、実験を組んで回した
    - 判定器はJevの代わりに[[Qwen3.8-27B]](vLLM)のlogprobs。max_tokens=1でYesとNoの確率を読む
    - 比較に[[ruri-v3]]の埋め込み(310m)とreranker(310m)
    - corpus: 公開されているLLM Wiki 11個のindexを束ねて、799行の肥大化したindexを合成した
    - 質問: ページ名や説明文の語をなるべく使わない言い換えの質問50問。Opus 5.5が書いた
- 結果(Hit@1、50問、説明文はindexの行+本文の冒頭)
indexの肥大化への対策
| 方式 | Hit@1 |
| -- | -- |
| index全体をQwen3.8-27Bに読ませて選ばせる(1問22.6万トークン) | 0.64 |
| ruriの埋め込みだけ | 0.58 |
| ruriのreranker(質問と文書を一緒に読む) | 0.80 |
| ruriの上位50件→Qwen3.8-27BでYes/No | 0.92 |
- 効かなかったもの
    - wikiを先に選んでからページを選ぶ2段(論文の木): 1段目で正解のwikiを50問中16問で落とした。Hit@1は0.40(短い説明文)
        - wikiの説明文にはREADMEの段落を機械的に使った。人が書いた説明なら変わるかもしれない
    - 799件を50件ずつ並べて全部判定する: 埋め込みで50件に絞ってから判定するより悪い(短い説明文で0.40対0.64、25問)
    - 候補を並べる効果(論文Fig. 6): [[lenchi]]の45問で、1件ずつ判定するのと差が出なかった(10勝9敗)
- 二人の論点と照らすと
    - 木が危ういのはkazunoriさんの言う通りの形で起きた(正解のwikiを1段目で落とす)
    - 埋め込みだけでなく判定器として使うのが効くのはkennさんの言う通り(0.58→0.80→0.92)
    - 一方「全部を文脈に入れれば精度も速度も上がる」は、この近似では逆だった。全部読ませると0.64で遅い
        - 学習したJev型のモデルで文脈が大きくなれば変わるかもしれない。Jevでは試していない
    - いちばん良かったのは「埋め込みで候補を出し、判定器で選ぶ」という混ぜた形だった
- 割り引いて読むところ
    - 50問と小さい。質問はページ本文から作ったので、本文を含む長い説明文に有利な作りだった
    - 判定器はJevでなくQwen3.8-27Bのlogprobsによる近似
- LLM Wikiへの含意
    - 1つのwikiのindex.mdは木でなく平らな一覧なので、「埋め込みで候補→判定器で選ぶ」はそのまま使える
    - wiki森を横断するときも、wikiを先に絞らず全ページを埋め込みで探すほうが安全

- 追試(2026-11-05〜06): 同じ公開LLM Wiki 11個・50問で、grepしながら読むagentと比べた
grepしながら読むagentとの比較
| 方式 | Hit@1 | 1問あたり |
| -- | -- | -- |
| Opus 5.5にwikiのcloneだけを渡す(Claude Codeの普段の運用) | 0.96 | 6.8万トークン、20秒 |
| Opus 5.5+上の検索の道具(ruri上位50→Qwen3.8-27BでYes/No) | 0.98 | 5.6万トークン+道具、83秒 |
| 検索の道具だけ | 0.92 | 20秒 |
| Qwen3.8-27Bにgrepとsed -nで探しながら読ませる(16Kの文脈) | 0.92 |
| Qwen3.8-27Bにindex全体を読ませる | 0.64 | 22.6万トークン、92秒 |
- Opusはgrepを中心に探し、index.mdを見たのは50問中13問だけ
    - 道具を渡すと全問で使ったが、道具の1位が外れた9問のうち8問は自分のgrepで直した。道具で増えた正解は1問
- Qwen3.8-27Bの「探しながら読む」は[[You don't need long context]]([arXiv 2611.05306](https://arxiv.org/abs/2611.05306))の形
    - index全体を読ませるのに17勝2敗、検索の道具とは3勝3敗
- わかったこと
    - indexの肥大化に効いたのは、新しい検索の道具より「全部読ませず、grepで探しながら読ませる」こと
    - Opusはすでにそうしていて、27Bでもその形をとれば検索の道具と並ぶ
    - 判定器による検索が要るのは、grepを使えない一発の呼び出しで小さいモデルにページを選ばせる場面くらい
- 割り引いて読むところ
    - 質問はページ本文から作ったので、本文の数字や語で探せるgrepに有利。Opusも「2,079」のような数字でgrepして当てていた
