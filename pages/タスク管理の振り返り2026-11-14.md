[[2026-11-14]] 散歩中にCodexと音声で話した内容の整理。
- [[散歩しながらCodexと音声会話]]

人に話すことで考えがまとまる
- [[未踏ジュニア成果報告会2026]]で、自分がタスクを管理する仕組みを作っている話をし、その結果として思考がまとまった感じがある。
- 今回も、会話することで言語化が進むといいと思っている。

特定のエージェントに縛られない包括レイヤー
- 成果報告会では、AIエージェントをCLIで使うか、Claudeアプリのようなものを使うかという話で盛り上がった。
- アプリで会話をフォークするとき、どこから分岐するかを選ぶ操作は楽。Claude CodeのCLIで人が直接コマンドを打つのは面倒。
- ただし、CLIをラップする層があれば、そこから操作できればよい。
- Claude CodeだけでなくCodexなど複数社のエージェントを使うので、特定の企業にロックインされずに、それらを包括する層が必要。

現在の仕組みと残る問題
- タスクごとにtmuxを立て、その中でCLIを動かし、それぞれのtmuxをブラウザから見られるようにしている。
- tmuxの中でどのCLIを呼ぶかは自由なので、特定の企業に縛られない共通のインターフェースになっている。
- 各エージェントがLLM Wikiを使う前提で、ワンボタンでfile backのコマンドを実行できる。
- 現状は一台のマシンのtmuxと密結合だが、実際にはタスクは複数のマシンに散らばっている。
- エージェントが別のエージェントを呼んだとき、特にマシンを跨ぐ場合、依頼と結果待ちの追跡に失敗しがち。
    - 「呼び出して結果を待っています」のまま、根元のターミナルを閉じてしまうと、何を待っていたか分からなくなる。
    - タブが開いていることでしかタスクの存在を覚えていないと、うっかり閉じたときに見失う。

接続し直してもタブの順番が失われる
- 以前はVS Code RemoteでSSH接続し、タスクごとにtmuxを立て、ターミナルのタブとして並べていた。
- tmuxを挟む前は、ネットワークが切れるとセッションが切れ、タスク自体が中断するのが問題だった。そのためtmuxを挟んだ。
- EC2のセキュリティアップデートによる再起動、MacBookの更新、VS Codeのクラッシュ、ネットワーク不調による接続断も起こる。
- VS Code Remoteに再接続してtmuxにアタッチし直すと、人間が整理するために並べ替えたタブの順番が消える。
    - タスクの実行が続いていても、人間が整理したコンテキストは失われる。

タブの並べ替えと二次元の空間配置
- [[タブUI]]で自由に並べ替えられることに価値を感じている。
    - これは一次元に制約された[[並び替えは貧弱KJ法]]ではないか。
- AI以前は、iPadのA4の手書きノートでタスクを管理していた。
    - 投げ縄ツールでタスクを囲み、好きな位置へ動かして、二次元に空間配置できるのがよかった。
- 一次元では表現しきれないコンテキストが、外部化されず人間の脳の中に残っているのではないか。
    - そうすると、その情報はコンピューターやAIから見ることができない。

人がストレスなく進められること
- [[GTD]]（Getting Things Done、ストレスフリーの仕事術）は、気にかかっていることを全部書き出すことをよしとしている。
- 人間の心の中に留まっている状態を、もっと気軽にアウトプットできる仕組みがあるといい。
- [[タスク付箋]]ともつながる話。

会話と書き戻し
- 会話のたびに書き戻すと待ち時間が長くなり、会話がスポイルされる。
- 一通り話し終わって、ひと段落ついたタイミングでまとめて書き戻す。

非集権的ソフトウェア生産
- 言語化の摩擦には、UIが自分の好みに合わないことも含まれる。
- 多くの人が一つのソフトウェアを使い、人間の側が合わせてきたところを、コーディングエージェントの進歩によって、各人が手元で自分に合う道具を作り、使いながらチューニングしていけるべきではないか。
- これを「非集権的ソフトウェア生産」と呼ぶのがよいかもしれない。

UIの調整と、AIが情報を入手できることは分けて考える
- 人間が散らばったタスクの全体像を把握する一歩手前に、まずAIがその情報を入手できるようにすることが重要。
- これは、UIを自分の手に合わせる話とは一旦切り離して議論する。

今の作業の仕方（2026-11-14の本人の説明）
- 普段はMacのVS Code RemoteからEC2とgalleriaに接続し、タスクごとのtmuxをターミナルのタブに並べて作業している。
- 一部はiPhoneからtmuxの画面を見られるようにしている。
    - これはMacの前にいないときにも作業する目的で作ったもので、現状で俯瞰できるのはgalleria内のtmux。
    - 複数のマシンにある仕事全体を俯瞰できているわけではない。
- 情報を入手できるようにする部分はかなり進めたと思っているが、全部できているかは把握できていない。

今回の気づき：実際の仕事との照合がまだできていない
- AIが今拾えている仕事だけを見ても、拾えていない仕事の存在は分からない。
- Mac、galleria、EC2に実際にある仕事と、AIが情報を取れる仕事を突き合わせて、取りこぼしや読めない部分を確かめる必要がある。
- これはやるべきだが現状やっていない、という重要な気づき。
- 新しい仕組みの評価では、それ以前の人間がどのように仕事を把握していたかとも比較したい。

VS Codeとtmuxで、人間が何を読み取っているか
- タブに見えるのは、AIが決めた要約を短く切り詰めた文字列であり、情報としては貧弱。
- タブを開くと、実行中か、質問・相談待ちかが分かる。
    - まだ人間の回答を求める状態でないものを開き、読んで確認する時間がかかっている。

質問を見たその場で判断できること
- 人間への相談待ちでも、質問文だけでは何を聞かれているのか分からないことがしばしばある。文脈情報が足りない。
- チャットUIでは「質問の意味が分からないので解説して」と送って返事を待つことになり、その間に人間のアテンションが途切れる。
    - 質問のすぐ横に背景・選択肢・必要なら辿れる根拠がまとまっていれば、その場で理解して判断しやすい。
    - 質問を見たその場で、背景を理解して判断まで進められることが必要。
- そのための画面として、チャットUIがよいのかを考えたい。

既存の文字列表示とキー送信を育てる案
- 現在のtmuxを包むWebサービスには、一覧を見る、tmuxに入る、という経路がある。
    - tmuxへの接続は高コストなので、接続せずブラウザ上で出力された文字列だけを読み、ブラウザからキー入力だけ送信する機能もある。
- この文字列表示の部分をリッチにする方向が考えられる。
    - まず、各AIから出力を収集する仕組みで、何がどこまで取れているかを把握したい。
    - ユーザーに何を問い合わせているかが取れているなら、関連情報をブラウザだけで読み、返信できるようにする方向へ進めそう。
- <img src='https://scrapbox.io/api/pages/nishio/Codex/icon' alt='Codex.icon' height="19.5"/> 今回確認した収集器には、直近の依頼・AI返答・未回答質問の抜粋を扱う実装があった。一方、元のAIへの返信は会話への入口を案内する作りで、tmuxの文字列表示・キー送信とは別の仕組みだった。全マシンの実際の仕事との照合は、今回まだ行っていない。

更新頻度が高い現在状況の保存
- LLM Wikiは、比較的更新頻度の低い知識を整理し、知識のネットワークを作るのに向いているのではないか。
- プロジェクトの現在状況や誰の返事待ちかは更新頻度が高く、古くなりやすい。この情報に適したストレージが必要なのかもしれない。
- <img src='https://scrapbox.io/api/pages/nishio/Codex/icon' alt='Codex.icon' height="19.5"/> 調べた収集器にはSQLiteと観測時刻・有効期限を扱う仕組みがすでにあった。新しい保存先を作る前に、既存の仕組みで何が保たれるかを確認する。

明日以降、何がどうなるとよくなるか（検討する案、未実施）

- 一つの質問について、ブラウザで背景を読むところから返答まで済むか確かめる。既存の収集と文字列表示・キー送信をどうつなぐかを考える。

音声での振り返りの経験へのフィードバック

- まとまった量を一気に話すと、Codexが「長いので整理するね」と整理を始めるところが面白い。
- 「少し待ってて」とよく言う。
- 口頭の指示でもソースコードを読んで、現在の実装がどうなっているかを回答できるのはよい。
- ウォーキング中は、待ち時間にも別の作業を始めず、このテーマに居続けられる。
    - PCの前では「少し待ってて」と言われると別のことを始めてしまうが、歩いていてキーボードもモニターもなく、音声だけでつながっているので、別のタブや作業へ離れにくい。
    - ずっと考え続けなければいけないわけでもない。単に歩き、頭の中が文字でいっぱいではない空間ができる。
        - その余白が、新しいものがふっと上がってくることを可能にするのではないか。
- 散歩中に音声で指示し、3つのサブエージェントを立ち上げて並行作業を進めた。

- 前回は、AIプロジェクトマネージャーの試みの中で行った音声実験だった。

    - 当時は事前プロンプトを入れられず、その知識を音声会話で使うことができなかった、と記録されている。
- 今回は、会話の途中でgraspから過去の記録を取り出せている。現在の作業状況の確認や、そのまま作業を依頼することにもつながっている。
    - 当時は文脈を接続できなかったが、今はgraspを接続できていることで、選択肢や可能性が広がった感じがある。

今回使っている音声機能の呼び方
- 今回は、Codexのタスクに音声で話しかけて作業を進めている。
- 音声機能自体の公式名は「ChatGPT Voice」。公式ドキュメントではCodexでも使えると説明されている。
